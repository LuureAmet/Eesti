# Working in fint/

This is one project inside the **Eesti** monorepo. It is self-contained: its
docs, tests and dependencies all live under `fint/`. Do not reach into sibling
project folders.

Claude Code reads this file automatically. Keep it operational — the *why*
lives in [`docs/07-PROJECT-MEMORY.md`](docs/07-PROJECT-MEMORY.md); read that
too before making design decisions.

## What this is

A filesystem intelligence engine: inventories files, hashes them with BLAKE3,
tracks what changed between scans, computes genuine duplicate waste, and lets a
user compose their own saved queries ("lenses") without writing SQL.

Python + SQLite backend, one HTML file frontend served by FastAPI. No Node, no
build step, no Docker.

## Commands

Everything goes through `fint`. **Use `./fint`, not `python3 fint.py`** — the
launcher pins the interpreter (see gotcha 1 below).

```bash
./fint doctor            # dependency + layout check, with cost of each gap
./fint status            # what the database currently knows
./fint scan PATH --profile light --secrets
./fint dupes             # duplicate grouping + reclaimable bytes
./fint report            # terminal report (--json for cron)
./fint backup            # snapshot + SQL dump + schema, one archive
./fint serve -b          # dashboard on 127.0.0.1:8420, backgrounded
./fint test              # all three suites — run before every commit
```

## Before you commit

```bash
./fint test
```

100 checks across three suites. They build a real filesystem — with hardlinks,
symlink loops, a planted AWS key — scan it with the actual scanner, and assert
the numbers. If you change scanning, duplicate maths, the lens compiler or
backup, add a check rather than trusting the change.

## Hard rules

1. **Nothing in this codebase deletes a user's file.** Cleanup is *emitted as a
   shell script* for a human to read — dry-run by default, re-verifying each
   file's BLAKE3 before removal, never listing a master copy. Keep it that way.
2. **The API opens the inventory read-only** (`mode=ro` + `PRAGMA query_only`).
   It may write only its own tables: `lenses`, `reports`, `file_tags`,
   `rescue_candidates`.
3. **`api/lens.py` is the only module that writes SQL.** Everything else emits
   a JSON AST. Never build a query by string concatenation anywhere else — an
   LLM writes these specs, so the compiler is the security boundary.
4. **Reclaimable ≠ occupied.** User-facing duplicate figures use
   `reclaimable_bytes` = `size × (distinct_inodes − 1)`. Reporting the sum of
   all copies as "savings" was the headline bug in v2.
5. **`file_events` is append-only.** Never update or delete a row. It is the
   only record of history that cannot be regenerated by rescanning.
6. **The ajalugu tool only copies.** It never deletes from or moves a backup.

## Gotchas that will cost you an hour

1. **Two Pythons.** An agent's shell may sit in one venv while the login shell
   uses the system python. Dependencies installed once appear missing to the
   other. `./fint` resolves `FINT_PYTHON` → `./.venv/bin/python3` → `PATH`.
2. **Scope is not a path substring.** `proj/.venv/x` is `cache` scope even
   though the path contains neither `.cache` nor `backups`. Filter on the
   `system_scope` column, never on text in the path.
3. **`blake3` is often NULL** — symlinks, empty files, unreadable files, and
   everything under `--profile fast`. Always guard joins on it.
4. **`--profile light` skips `node_modules`, `.cache`, `.venv`.** An empty
   query result may mean "not indexed", not "not present". Say so rather than
   reporting absence as fact.
5. **The missing-file sweep keys on directories actually visited**, not on the
   scan root. That is what lets subtree scans coexist and stops a profile
   change from faking deletions.
6. **Hardlinks are one file.** Two paths sharing `(device, inode)` occupy the
   disk once; "deleting the duplicate" frees nothing.

## Layout

```
fint / fint.py       CLI (launcher + dispatcher)
scripts/scan.py      walker, hasher, classifier, upsert, audit events
scripts/process_duplicates.py
scripts/rescue_ajalugu.py
scripts/fi_common.py     connections, versioned migrations
scripts/fi_classify.py   category/language maps, scope rules, secret patterns
sql/10_views.sql     curated views — the frontend/lens contract
api/lens.py          JSON AST → parameterised SQL
api/main.py          read-only REST API
web/index.html       the dashboard, one file, no external requests
tests/               three suites, ~100 checks
```

## Migrations

`PRAGMA user_version` + an ordered list in `fi_common.MIGRATIONS`. **Never edit
a released migration; append a new list.** Do not reintroduce `try/except: pass`
around schema changes — a bare except cannot tell "column exists" from "disk
full".

## Style

Match the surrounding code. Comments explain *why*, not *what* — particularly
where a non-obvious choice was made (why the online backup API instead of `cp`,
why an AST instead of SQL). Those comments are load-bearing.
