# Roadmap

Ordered so that each stage is useful on its own and adds no infrastructure until
the previous stage has proven it is needed. Stages 0–3 are **done and tested**
in this repository. Stages 4+ are designed, not built.

## Stage 4 — Text extraction and search ⬜ next

**Trigger to build:** you want to search file *contents*, not just paths.

The critical decision is to keep extracted text in a **separate database file**.
Injecting tens of GB of text into `files.db` would make every trivial metadata
query ("how many PDFs?") slow, because SQLite pages interleave.

```
files.db        metadata, history, duplicates   — stays fast, stays small
files_text.db   extracted content + FTS5 index  — grows freely
```

Join at query time with `ATTACH DATABASE`. `fi_common.TEXT_DB_PATH` already
points at the right location, and the `file_text` / `file_text_fts` tables from
the existing schema move there unchanged.

Work required:
- `scripts/extract_text.py` — reads `files.db` for candidate paths (by category
  and size), extracts text, writes to `files_text.db`, populates FTS5
- A `v_text_search` source in the lens registry, so full-text becomes just
  another lens condition rather than a bolted-on search box

**Do not** add embeddings in this stage. FTS5 with a porter tokeniser answers
most of what you will actually ask, at zero infrastructure cost.

## Stage 5 — Agent attribution ⬜

**Trigger:** you want to know *which* agent touched a file, not just that it
changed.

`file_events` already records what changed and when. Attribution needs a source
of "who was running at that time". Two options, cheapest first:

1. **Path convention.** `ai-mailbox/inbox/<agent>/…` already encodes the agent
   in the path. A lens over `v_agent_activity` grouped by `parent_dir` gets you
   most of the way with zero new code.
2. **An `agent_actions` table** written by the agents themselves (agent name,
   action, path, timestamp). Join to `file_events` on path + time window.

Option 2 is the one that supports the "AI Court" idea, and it needs cooperation
from the agents — the scanner cannot infer authorship from the filesystem alone.
Be honest about that boundary: the scanner provides immutable *evidence* of what
changed; it cannot provide *attribution* on its own.

## Stage 6 — Public transparency portal ⬜

**Trigger:** you actually want outsiders looking at this.

The design is sound and the groundwork exists: `contains_secrets` and
`secret_types` are already populated by `scan.py --secrets`, and the engine
deliberately stores the *kind* of credential, never the value.

Requirements before exposing anything publicly:

- A **separate read-only export database**, generated by a filter script. Do
  not point a public frontend at your working database, however read-only the
  handle claims to be.
- Path redaction rules — a path is itself information (usernames, project
  names, client names).
- An explicit allowlist of directories to publish, never a blocklist.
- Rate limiting, since every lens is a query.

Transparent redaction — "this file exists, contains 1 database password and 2
API keys, contents withheld" — is the genuinely novel part and is directly
supported by the current schema.

## Stage 7 — Scale-out ⬜ (probably never)

Written down mainly so it can be argued with, since it was proposed as phases
3–4 elsewhere.

| Migration | Justified when | Current state |
|---|---|---|
| SQLite → PostgreSQL | >5M rows, **or** concurrent writers, **or** network access from several machines | 282k rows, single writer, local |
| Vector DB / embeddings | FTS5 demonstrably fails at questions you actually ask | FTS5 not yet populated |
| Neo4j / graph DB | Traversals more than ~4 hops deep, or genuinely unbounded path queries | Every described query is a join or recursive CTE |
| Docker | You need to deploy this somewhere other than the machine it indexes | It indexes this machine |

SQLite at 282k rows with the indexes in `10_views.sql` answers every dashboard
query in milliseconds. Migrating to Postgres now buys latency, an ops burden,
and a second thing that can be down — and buys back nothing.

The one measurement that would change this: if `scan_statistics.duration_seconds`
climbs past a few minutes on a light-profile scan, or if the API's p95 exceeds
~200 ms, revisit. Both are already recorded, so the decision can be made from
data rather than from vibes.

## Suggested cadence on the real machine

```cron
# hot tree, hourly, cheap
0 * * * *  cd ~/file-intelligence && python3 scripts/scan.py ~/ai-mailbox --profile light

# full home, nightly
30 3 * * * cd ~/file-intelligence && python3 scripts/scan.py ~ --profile light --secrets \
             && python3 scripts/process_duplicates.py

# backups, weekly — they change rarely and hashing them is expensive
0 4 * * 0  cd ~/file-intelligence && python3 scripts/scan.py ~/backups --profile full \
             && python3 scripts/rescue_ajalugu.py --scan
```

This is the payoff of the visited-directory missing sweep: these three schedules
operate on independent subtrees, mix profiles freely, and cannot mark each
other's files as missing.
